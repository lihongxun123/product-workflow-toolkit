# 表达模式与改写示例

这些是编辑线索。结合用途和上下文判断；单词命中不构成问题，规整的术语、表格和规范句式可以保留。以下示例只展示各自原文已有信息的重组，不给实际项目增加规则。

## 先查事实与状态

| 线索 | 核对与处理 |
| --- | --- |
| “研究表明”“专家普遍认为”却没有来源 | 核对具体依据；没有依据时删去归因或说明缺口，不直接断定原结论为假 |
| “已全面实现”“稳定可用”“确保成功” | 核对证据支持的阶段和范围，保留真实确定程度 |
| 将规划、建议或原型写成已上线能力 | 按当前来源修正状态 |
| 只有部分观察，却推断所有用户或整个市场 | 收回过度概括，说明推断依据及适用范围 |
| “当然”“以下是”“希望对你有帮助”出现在正式正文 | 删除聊天包装，直接呈现内容 |

## 防御性文案与真实限制

删除为编辑者自我辩护、重复提醒或强调无关未做事项的句子。涉及费用、权限、风险、责任、未验能力及关键反例时，判断其是否影响读者使用，再决定保留或合并。不要把“不”“仅”“不得”“不代表”列为禁词。

**直接写完成条件**

原文：鉴权成功不代表任务完成，请勿把鉴权成功误认为任务成功。只有客户端完成指定操作或返回所需结果，才算任务完成。

改后：客户端完成指定操作或返回所需结果，才算任务完成。

**保留验证范围，删除重复免责**

原文：目前已通过 Windows 模拟网关验证。需要强调，这不意味着 macOS 或真实渠道已通过，不能把模拟验证视为正式渠道验收；macOS 和真实渠道均待验。

改后：Windows 模拟网关验证通过；macOS 和真实渠道待验。

**保留会改变行动的条件**

原文：验证按每次请求计费；报价失败时不得发起验证。请注意这里并未承诺验证免费。

改后：验证按每次请求计费；报价失败时不得发起验证。

共用条件放一处，具体例外就近说明。若多个段落可被独立使用，各处可保留理解该段所必需的短提示。

## 冗余与结构

| 问题 | 处理 |
| --- | --- |
| 标题、开场、正文和结尾反复说同一句话 | 保留读者最需要的位置，删除重复解释 |
| 名词堆叠、空泛宣传，如“赋能”“能力建设” | 回到材料中的对象、动作和结果，缺事实时不要补造流程 |
| “大幅提升”“显著降低”缺指标 | 有证据则说明数据及范围；否则收回无法支撑的效果判断 |
| 每节固定“背景—意义—风险—下一步” | 按内容组织，只保留有用部分 |
| 用大量加粗标签、碎片短句替代解释 | 能连贯说明的改为自然段，并列与比较再用列表或表格 |
| 同一对象交替使用多种近义词 | 沿用项目已有准确术语 |
| 为显得完整而强行凑三项或五步 | 保留实际存在的项，不补无用栏目 |

**将抽象包装还原成规则**

原文：为推进审核机制完善、构建内容治理能力，运营需在审核工作台处理待审内容，拒绝时填写原因。

改后：运营在审核工作台处理待审内容，拒绝时填写原因。

判断一段是否有用，要看它是否帮助理解事实、形成判断、完成操作或说明必要条件；连接上下文的过渡和解释也有价值，不要求每段都塞入一个新事实。

## 精简时的保留项

- 不弱化“必须、不得、默认、仅”等规范强度。
- 保留名称、字段、代码、命令、路径、来源及引用的准确性。
- 不为顺畅删除关键反例，或把“观察到”弱化成“可能”、把“部分样本”扩成“全部”。
- 原文不完整时具体指出缺口；新稿只从当前材料补充事实。
- 按文体保留必要的禁止条件、风险提示和责任说明，删其重复包装。

## 扫描结果怎么用

只读扫描器的 p0/p1/p2 表示候选复核顺序，不是内容真伪、严重事故或作者身份的判定。代码、引用和明确有依据的表述可能无需编辑；脚本不理解跨段重复、条件依赖或完整证据，仍需阅读上下文。不要为了清零命中数修改准确内容。
