# 需求正文与任务摘要

以下结构可合并，不要求每条需求都使用表格、规则编号或同样篇幅。

## 详细 Markdown

- 标题：需求编号、模块与具体目标；附任务链接和已确认的原型深链。
- 问题与目标：谁在什么场景遇到什么问题，要达到什么结果。
- 范围：功能、页面与入口；仅保留影响实现的站点差异和职责边界。
- 页面与规则：内容、数据来源、默认值、操作、校验、成功结果；多步骤流程写完整续接和返回。
- 状态与异常：按实际业务覆盖加载、空数据、失败、权限、取消或恢复，可直接并入对应规则。
- 验收：给定条件和操作后的可观察结果，与规则对应。
- 用到图示时参照下文的[需求图示](#需求图示)。

验证保存失败后的重试时，可检查两次回读结果。首次保存失败后，表单仍显示已填内容，详情仍显示原值。用同一内容重试成功后，重新打开详情可读到新值。

不要把“R02、R04”等追踪编号作为规则替代品。例如在活动满员时开放候补，应注明何时检查余位、余位变化时页面如何恢复，再按需链接关联需求；不要把这个示例复制为所有产品的要求。

## 需求图示

- 图放在对应的 Markdown 段落，沿用正文的业务名称。涉及付款、核销、奖励等不同对象时分别表示。状态与异常较多时，可用表格写明触发条件、用户反馈、系统处理和恢复条件。图表替换重复叙述时保留计算依据、例外和验收条件，业务状态的命名不限定数据库枚举。
- 按关键路径核对资格检查、分支、终态和重试。例如暂缓与失败要分开，已入账后重试同步只重试同步步骤。跨端或跨服务图写清各方职责，标明既有能力与待实现行为，说明相关的鉴权、数据归属、提交或生效时点；涉及并发、幂等、重试或补偿时再画出对应路径。
- 过宽的图按业务环节拆开并标明衔接，节点用短句和自然换行。最后一次修改后实际渲染受影响图表，在常规阅读宽度检查字号、换行、遮挡和分支。任务平台不能渲染 Mermaid 时，保留同一份 Markdown，注明可用的阅读器；按用户要求另附图片。

## 简洁任务正文

通常用一个目标句、若干并列实施点，以及原型和附件链接即可。长度以不遗漏关键决定为准，不设置硬性字数限制。

例如一个新增邮箱密码登录的摘要，应保留：原有登录方式的默认与优先级、密码入口适用的账号、成功回跳、失败处理，以及不改变的注册规则。具体渠道、默认方式和错误文案必须来自该项目决定，不能从这个示例推断。

任务系统正文和详细 PRD 不是两套规则：修改一个关键默认值时，两者对应位置一起更新；执行状态仍留在状态字段或现有评审清单。

## 交付前自检

- 研发只读正文和原型，能否知道输入什么、点哪里、结果是什么、失败怎么办？
- 每个决定有依据吗？是否混入了建议、旧版本或模拟数据？
- 删除内部话术后，是否误删了权限、单位、失败恢复或必要职责边界？
- 同一功能是否被多个需求重复承接？编号、标题、附件和路径是否一致？
- 外部同步与本地准备的完成状态是否准确，是否擅自变更了排期或下发状态？
