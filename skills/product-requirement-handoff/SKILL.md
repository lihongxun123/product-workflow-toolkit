# 研发需求文档与任务交付

一项需求维护一份需求文档，供产品、研发和测试共同理解与验收；任务系统呈现可执行摘要。内部核查记录沿用现有证据文件，保存源码、历史决定、推导及验证过程，不随需求交付，不另建“内部版／研发版”两套需求。内部记录链接需求文档，需求文档不反向暴露内部核查链接。排期和产品确认状态由既有评审入口承接。

随包文件路径相对于当前 Skill 目录。用户需要阅读参考正文或体验案例时，从随附文件读取对应内容，按需要展示或导出。

## 先确定当前版本

读取该需求当前主稿、最新用户决定和必要原型证据，确认编号、模块、目标端与站点、合并或拆分关系。已有项目模板优先使用。不要因历史文件名含旧模块就猜测需求归属，也不要用代理建议填补已确认规则。

局部润色保留准确条款、必要的追踪ID与引用、数量、条件强度和异常边界，不全篇重写。正文使用业务名称，追踪ID用于对应任务。清理结构时，引用优先指向当前真实标题；删除旧锚点前检查并修正受影响链接，仅在确有兼容需要时保留。需要新写时参照正文与任务摘要（`references/document-shape.md`），按复杂度裁剪，不补空章节。

研发处理清单按问题列出影响对象、已观察的现象和复测通过条件；根因尚未核实时写清研发要核实什么。请求编号和日志引用现有证据。

## 精简的范围与取舍

先区分文字精简与产品方案删减。只改表达时，删除重复、过程说明和无决策价值的技术细节，保留既定功能与验收强度，不自动修改原型或外部任务。涉及删除功能、改变默认行为、恢复规则或需求归属时，先说明影响；已有明确决定或用户已批准具体建议，直接按该范围推进，不重复确认。

以用户完成任务所需的最小闭环判断复杂度：优先复用已有数据、能力、权限和组件，避免重复维护、作用重叠的设置及缺少使用依据的便利分支。权限隔离、合法输入、失败恢复、状态生效和历史数据保护按实际风险保留，不能以篇幅短为由删掉。其他需求负责的流程只保留必要衔接与归属；具体表结构、接口或缓存实现仅在已有明确约束时写入，不替研发预设方案。

已批准的方案删减同步到受影响的主稿、摘要、原型、图示和验收条件，避免只删文字或隐藏按钮而保留旧行为；按本次授权分别处理本地修改与外部同步。图只覆盖当前需求的关键职责和分支，不为完整展示整条系统链路而扩大范围。

## 面向研发写清规则

- 先写用户或业务实际问题，再写最终方案；不以原型调试中的缺陷冒充线上现状。
- 按内容性质组织：概述用短段落交代目标和范围，操作按业务发生顺序展开，条件与结果较多时用判断表，不同对象用对比表；异常紧跟相关环节，示例就近说明难点，记录要求和验收条件保持可查。按实际内容选用，不给每份需求套同一流程或强制表格化。
- 重整须拆开混合内容、归并散落规则，把条件、动作和结果放回对应环节，再用具体业务对象与动作命名标题；不只替换“范围与改动”“实施规则”等标题，也不为统一格式给每段加标题。尤其区分资格判定、实际生效和异常恢复的时点，避免重排后改变条件适用范围或先后关系。
- 关键动作交代条件、默认值、操作、校验、成功变化及失败恢复。字段只写需要实现或判断的名称、来源、单位和可选值。
- 跨需求引用使用业务名称和必要链接，说明谁提供什么数据或结果、本项如何使用及异常时如何处理，不以编号或“详见”代替规则。区分已核实可用的功能、需要补做的功能和需要研发核实的部分；引用另一份需求不等于该功能已经实现。只补足理解本项所需的内容，不复制整份依赖文档。
- 规则优先用业务名称分节，操作顺序、需要追踪的验收项保留必要编号；不叠加页面号、章节号和规则号。源码位置、历史决定、核查链接和编辑过程归入现有内部核查记录，不放在需求文档末尾充作参考资料；其中影响实现的缺口转成明确改造要求，不能随证据一起移走。原型入口和必要业务依赖保留，不把可操作链接误作内部维护信息删除。
- 保留会改变实现或验收的业务边界。研发需确认已有实现、接口、负责人、旧数据处理和联调顺序；具体技术实现不列为产品待定。只有出现改变业务规则或旧权益的真实冲突才回产品决策。已确认需求不设空泛“待确认”章节，实质缺口须明确说明。
- 去掉“本轮”“本地评审稿”“任务描述草稿”“详见实现记录”等过程话术；不用版本/日期/作者行堆叠内部管理信息，除非项目或用户确有要求。合法业务日期和有效期不能删。
- 将测试执行记录、模拟器说明、提交和部署过程与产品规则分开。验收标准写可观察结果，不写“验证通过”等执行状态。
- 验收覆盖本次变化的主路径和必要异常；不为普通页面新增密码找回、审批、团队管理等未经确认功能。

交付前按未参与讨论的研发人员检查：能否从正文说清本项做什么、哪些功能可沿用或仍需补做、与其他需求交换什么结果，并据此拆任务。选一个正常场景和一个关键异常，不翻聊天历史或依赖文档也能判断本项结果和验收方式，并找到对应原型。再对照改前稿核对范围、起算点、计算依据、例外及验收条件，避免改写扩大或缩窄规则。检查发现的问题直接修正，不另建例行检查文档；链接有效或原型能打开不能代替上述检查。

## 按需补充流程图或时序图

当文字不足以清楚说明分支、状态流转，或前后端与多个服务之间的职责、先后顺序、异步结果和失败恢复时，在详细需求中补充图示：业务判断与状态路径用流程图，跨端或跨服务协作用时序图。简单页面增删改无需机械配图；只画影响实现和验收的关键路径，不扩大产品范围。

按业务过程重整不等于改成纯段落。多分支用流程图，状态及异常用表格交代触发条件、用户反馈、系统处理和恢复条件；付款、核销、奖励等不同对象分别表达，业务状态不直接规定为数据库枚举。图表替换对应的重复长段落，保留计算依据、例外和验收条件，原型入口仍可直接找到。逐条核对分支、终态及重试是否与正文一致，不能把暂缓画成失败、把已入账待同步画成重新入账，或将正常路径的资格校验省略。

流程图和时序图直接在需求 Markdown 正文中使用 Mermaid 代码块实现，与正文共用术语、条件和异常规则；不默认导出或上传独立图片。区分既有能力与需求新增行为，不把拟定接口或服务划分写成已实现事实。面向后端的图交代必要的鉴权、数据归属、提交或生效边界；仅在相关时说明并发、幂等、重试与补偿。

流程图过宽时按业务环节拆开，放回对应正文并保留衔接；节点用短句和自然换行，避免缩小字号或单字落行。最终修改后实际渲染复验受影响图表，检查常规阅读宽度下的字号、换行、遮挡、分支及图文一致性，不以修改前截图代替。任务平台不支持渲染时，保留同一份 Markdown 并说明用支持 Mermaid 的阅读器打开，不自动增加图片附件。

## 原型链接与附件

原型入口是研发操作材料，不属于应清理的内部维护链接。精简正文时保留可直接打开的入口及必要操作提示，不改成证据文档的间接跳转。同步任务系统时，将本地预览地址替换为已确认发布且覆盖本需求版本的线上完整深链，保留路径和必要参数；尚无对应线上版本则明确缺口，不能删除入口、猜域名或用旧版冒充。

默认交付为任务简述、一份有效需求 Markdown，以及已有可访问的原型入口。不重复附列表、配置、确认等原型截图，不另发流程图／时序图图片；截图和渲染验收记录留在内部证据目录，用户明确要求时再附。原型仅本地可用时，不在面向远程研发的任务描述中放 localhost 或本机文件地址；本地审阅材料可保留并标注限制。不以截图替代交互原型，也不为补齐链接擅自发布。

研发附件使用已确认发布地址的完整深链，保留路径与必要查询参数。用户要求本地审阅时可保留本地链接；不要凭空拼接未确认域名。发布地址已知但未实际检查时不能称为已验证。

正式交付或同步前确认链接实际页面及版本；仅草拟或润色时可复用仍有效的证据，不为措辞修改强制联网。没有核验时如实报告。静态发布不带本地模拟服务时，指出交付缺口，不把换域名当作适配完成。不把验证码、密码、令牌或真实私密草稿放入链接。

任务正文只写实施范围、关键规则、验收结果要求、详细附件和原型入口。拆分/合并关系只在影响职责时简短说明，不重复粘贴整份 PRD。

## 同步与收口

- “先本地整理”只保存本地；上传、修改任务正文或下发按用户明确授权执行。自动选用技能不等于自动取得同步权限。
- 同步前核对确切任务编号、现有正文和附件；保护未要求修改的负责人、排期和状态。
- 同步后回读标题、正文与附件，必要时校验附件内容/哈希。上传成功不能仅以点击上传按钮判断。
- 优先使用平台正常版本管理；旧附件保留时在正文指明有效附件，不创建无法区分的同名版本。删除按平台可恢复性及授权处理。
- 更新已有主稿和映射入口，避免再建一份“最新版汇总”。产品确认、文档上传、研发下发、原型验证和发布分别报告，不相互推导。

交付只说明实际完成项、文件或任务入口、必要未决项。不要用“全部Ready”覆盖逐项确认。
