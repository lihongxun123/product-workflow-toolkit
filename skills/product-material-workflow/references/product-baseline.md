# 产品基线与资料维护

用于新旧项目的产品方案、概览与架构，以及资料覆盖、主稿归属和历史整理。按本次任务选择相关部分，让协作者理解产品、追溯决定、定位规则并评估变更。

## 先明确这次要支持什么工作

从材料和用户请求确定读者、产品范围与完成条件：了解产品、研发实施、运营操作、查实现差距，所需深度不同。先读现有入口并列出候选主稿，再有针对性地读正文与依据；标题、文件日期、链接数量都不能单独判定完整性或权威。

“整体优化产品文档”包括现行正文的逻辑、行文和跨稿一致性，不能自行缩成目录整理。在授权范围内逐份判断需修改、检查后保留或冻结追溯；已符合要求的正文保留，不为凑改动重写。覆盖情况留在工作上下文或已有维护记录，不新建台账。用户只要求目录、局部编辑或只读审查时，按其范围交付。

旧项目先对照需求、源码／界面观察、交付与历史决定，区分既有事实、目标行为及未决差异。源码已有行为不自动成为正确规则；未实现的已确认需求也不能直接归为过时方案。

已有项目写方案或概览时，沿用有效业务事实和决定，按读者目的补齐关系或取舍，不重新执行接手盘点。需要新作产品选择时，使用下节方法；已确认的选择无需重新论证。

## 新项目与新方案的判断

先说明谁在什么场景遇到什么问题、目前如何解决、希望改善什么，以及已有证据和约束。没有用户或市场证据的判断保留假设身份；事实缺口先查证，方向取舍不清时使用 [需求澄清方法](clarify-scope.md)，也可调用已安装的 `clarify-next-step`，不要求用户填完整访谈表。

- 比较有实际差异的方案，优先复用或最小扩展，按需考虑人工处理或暂不开发。新增实体、页面、配置要解决具体业务任务；内部技术差异由系统承接，必要异常按触发场景处理。说明收益与维护代价，不为凑选项增加设计。
- 推荐方案写清选择理由，以及哪个关键假设不成立会改变推荐。记录最小可用路径与本次范围，保留已确认的必要功能及验收条件。
- 优先用成本较低、能区分方案的动作检验关键假设，如查现有数据、观察用户完成任务或试用现成工具。提出观察对象、结果和继续／调整／停止的判据；没有依据的数值阈值标为建议，不写成已确认目标。证据不足时结论是需要验证，不能直接宣称方案成立。

把问题、选择理由与验证办法融入本次方案或现有主稿；小任务可用一段话说明，不固定章节或新增验证台账。提出验证方案不等于已执行，也不自动授权开发、招募、付费或发布。

## 从产品逻辑组织架构

需要建立或调整架构时，从关键用户任务与已知业务事实出发，识别角色、业务对象、能力、模块及关系。资料不足的关系标为假设；不以同类产品有某模块为由直接纳入本站范围。

- 沿关键路径明确对象由谁创建、读取、改变和终止，状态、权限及费用在何处生效；只展开本产品相关部分。
- 按稳定职责划分模块，说明交接对象和共同规则。一个页面可能跨多个能力，一个能力也可能分布在多端；不把页面列表或源码服务图直接称为产品架构。
- 沿代表场景检查模块之间的衔接、共享规则的归属和必要异常。各自成立的模块不能拼成完整路径时，指出具体交接缺口。
- 架构图用于解释关系，可按需要画业务对象、能力分层或流程图；只有关系确实不同才分图，不强制每份文档配齐三图。图、术语和正文应一致。

把确认的结构维护到已有产品全景或主稿，细则仍由对应需求承接。目录按资料职责组织，业务架构按产品逻辑组织，不要求两者一一对应；技术选型与实现架构另按任务处理。

## 以问题检查覆盖，不以文件数检查

按项目需要确认下列信息是否能找到；小项目可放在同一份现有主稿，复杂项目才按独立维护需要拆开。

| 信息 | 应能回答的问题 |
|---|---|
| 定位与范围 | 为谁解决什么问题，主要路径是什么，哪些明确暂不做？ |
| 对象与规则 | 谁操作什么对象，条件、权限、状态、成功与失败怎样衔接？费用等只在相关时展开 |
| 决定与理由 | 哪些已确认、由什么依据支持、适用范围是什么，哪些替代方案已不采用，哪些仍待定？ |
| 实现与验证 | 需求、源码、原型、部署和实际行为分别有何证据，日期与环境是什么？ |
| 依赖与资料职责 | 哪份正文维护该规则，修改会影响哪些流程和资料，历史依据在哪里？ |

指出缺口时分清：没有资料、已有但入口遗漏、规则未确认、实现未完成、尚未验证。查找图或脚本只能证明可达性，不能据此给产品覆盖率或宣称全部完成。

## 指定主稿，再消除重复

资料职责通常包括导航、产品结构、规则正文、执行状态与历史证据；这些是信息职责，不是必建文件清单。优先沿用项目已有承接，找不到明确需求不要新增“最新版汇总”或并行台账。

目录按读者任务和稳定业务主题组织。同一层使用一致的分类依据，子需求进入所属主题；条目通常只需说明用途与必要边界，详细规则和逐项状态留在负责正文。新近完成的事项不因时间新而占据总目录首位。

整理目录时同时检查实际文件树、文件归属和 README 导航；只改入口文字不能算完成文件夹整理。需要迁移时核对机器引用与冻结附件，修正受影响的路径，并检查原文件完整性。

主稿效力依对象、站点／版本范围、明确确认与来源判断，不能按修改时间排序。跨对话先核最新进展与负责正文，区分本轮结束、业务待评审和真实验收；用户要求等待时，等相关执行结束再归并共享内容。先消解范围、单位、历史版本造成的表面冲突，只在现有评审位置留下证据仍无法解决的实质取舍。

比较疑似重叠稿时，识别独有的条件、例外、状态、权限、字段、验收及来源：

- 各有职责的正文保留，如业务规则、操作 SOP、页面细则；减少重复段落，不只因同主题就合并。
- 已被替代的批次保留日期和当时结论，连接现行承接；撤销旧“当前实施入口”的效力，不将整份历史改成今天的状态。
- 兼容跳转页、冻结交付附件、原始研究和证据不是可自动删除的重复正文。先查引用、唯一信息与追溯用途；未经相应授权不删除或重写快照。
- 独有规则进入明确承接后再精简旧稿。历史补充中仍有效的条件、优先级、计算依据和异常恢复须归入当前操作或规则，不能只归档全文、加一句“以最新为准”。保留日期对应的证据及被替代结论，以及受影响的文件链接、规则编号和锚点，或提供兼容跳转。

## 在自然变更中保留产品逻辑

日常讨论按 [SKILL.md 的“把已确认决定写回主稿”](../SKILL.md#把已确认决定写回主稿)执行，不重新盘点整个项目。业务规则修改后核对直接引用、摘要和受影响流程中的实际表述：范围、例外、参数和状态是否仍一致，不能只修链接或在文末追加相反结论。不能从实现反推未记录的动机。

状态记录区分确认、原型验证、文档下发、研发实现、部署与真实验收。旧交付记录不回写；新稿未同步时保持本地与已下发版本的区别。更新到现有评审／维护入口，不另建总台账。

## 需求变更与资料联动

仅在拆分、合并、延期或修改规则时读取；局部变更不重跑项目盘点。

- 按可独立理解、实施和验收的用户目标划范围，复用已有编号。合并说明保留项与来源项，拆分明确各项及共享能力归属；延期明确承接和触发条件，保留仍有效的依赖。负责人、排期和状态仅按授权修改。
- 核对目标端、站点与相关权限、计价和政策；共用页面不意味着规则相同。以当前需求、源码与实际行为判断复用、调整、新增或删除，原型缺失不能单独证明需要重做。
- 按变化追踪入口、结果与返回、登录后续接、共享组件、已有链接及其查询条件和刷新恢复；核对默认值、字段来源、筛选、单位、权限与必要异常。迁移后检查死链，兼容只覆盖已有地址或明确要求。
- 修改原规则及受影响的本地摘要、引用、图示和验收。原型改动按 `product-prototype-delivery`，研发正文与交付按 `product-requirement-handoff` 处理，范围以本次授权为准；冻结附件保留原记录，外部同步另依有效授权。

影响可直接在现有主稿或工作上下文记录，不为每次变更新增台账。

## 用实际阅读与变更任务验收

从本次读者任务选择代表路径：新人能解释产品主路径与职责；研发能确定规则、例外与验收；运营能完成操作并判断异常后怎么办；维护者能追到负责正文与历史依据。给出具体场景，依据成稿回答并定位条款；涉及取值顺序、金额或累计状态时，核对会改变结果的反例或算例。仍需拼接日期补丁、猜默认条件或请作者解释，说明正文尚未完成；链接可达不能代替这项检查。

按影响检查链接、锚点、编号及必要信息承接；先复用现成工具或项目脚本，不为一次整理搭建知识图谱或同步系统。结构变化查看实际渲染。跨模块或影响关键判断的整理做一次独立复核，修复后只复验受影响项。

覆盖结论分别说明逐份检查的范围与深入验证的代表场景，不把抽样通过扩成全部正文通过；区分资料可找到、规则可执行和产品已上线。已有结论仍有效就复用，不重复全量审查。后续沉淀只提取实际暴露的缺口和判据，复用已有技能，不把项目编号、业务参数或偶发问题扩成通用强制流程。
